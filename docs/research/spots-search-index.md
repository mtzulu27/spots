# Catalog-backed search

## Scope

Explore, map search, result counts and relevance reuse the same filtering/matching
rules. This change does not redesign UI, change budget inclusion policy, or
publish to Hostinger. A separate source snapshot enriches search without
overwriting catalog prices, budget scenarios or editorial tags.

## Sources of searchable facts

`apps/mobile/lib/spot-search.ts` builds and caches a document per immutable Spot
object from name/brand, branch/location labels, primary category, subcategories,
tags and moods, plus verified product evidence from `menu-search-index.ts`.
Refreshing catalog objects naturally creates new documents.

A new place is searchable from these fields without an ID/slug/name-specific
rule. New activities not listed in the shared vocabulary still work as literal
structured terms. The shared vocabulary adds reusable query equivalents, not
special exceptions for businesses.

Descriptions, bare links, generated category aliases and inferred characteristics
are deliberately excluded as assertions of services. Product names and specific
sections in sourced menus are evidence; promotional descriptions and ingredient
prose are not. Missing facts are not silently generated by an LLM.

## Verified menu evidence

- Prefer a freshly extracted public Menupp snapshot with the exact menu URL.
  It replaces older products for that source, preventing removed products from
  remaining searchable merely because an older transcription still lists them.
- Root URLs are resolved only for a single-location, single-menu source with one
  catalog branch and remain bound to that branch ID. Multi-branch root URLs remain
  pending, never copied between sedes. A newer verified catalog transcription
  supersedes an older source snapshot rather than being masked by it.
- Otherwise use existing catalog products with a source URL and a recorded
  verification date. Recognize legacy source field names; branch-level menu
  verification may supply the date/source. Do not substitute updated_at or the
  audit date for a missing verification date.
- Ignore explicitly unavailable products, disabled source menus/categories and
  products with no available presentation. Do not equate calculationIncluded=false
  with unavailable: a bottle or shared dish can be offered without being suitable
  for a per-person budget calculation.
- Exclude explicitly unconfirmed branch scope. Source refresh does not prove
  real-time availability, and older verification dates remain visible in the audit.
- Product names support arbitrary literal queries; shared vocabulary supports
  singular/plural equivalents and reusable product classes. For beverages use
  the product's classification: Corona under Cervezas is evidence of beer;
  pollo a la cerveza is not. A mixed Cerveza y Vino heading alone proves neither
  family for an unidentified product. Cerveza sin alcohol must be evidenced on
  one product, not assembled from regular beer plus an unrelated mocktail.
- Specific product sections can support discovery (Pepperoni under Pizzas).
  Modifier categories do not establish standalone offers in refreshed sources.
- No price is read into the search score or changed by this process.

### Refresh And Audit

```sh
# Public read-only HTTP acquisition, sequential, with source reports retained.
node scripts/spots-research/refresh-search-menus.mjs --refresh
# Resume an interrupted acquisition without re-requesting completed sources.
node scripts/spots-research/refresh-search-menus.mjs --refresh --resume
# Rebuild from this run's saved source reports, without network requests.
node scripts/spots-research/refresh-search-menus.mjs
node scripts/spots-research/audit-search-index.cjs
```

`SPOTS_SEARCH_RUN=YYYYMMDD` selects a run; otherwise use the date in Bogota.
The runtime snapshot is `apps/mobile/public/menu-search-sources.json`.
Reports, unresolved exact-source mappings, every branch's coverage, exclusion
reasons and per-product evidence are in `docs/catalog-review/search-menus-20261101/`.
The full-catalog audit is distinct from live acquisition: not all providers or
all branches have a verified/transcribed menu. Absence of evidence is not evidence
that a business does not offer a product. Non-Menupp transcripts participate when
their existing source/date/scope is sufficient; they were not all fetched again.

## Matching

- Normalize case, accents, punctuation and whitespace.
- Preserve multiword concepts before discarding conversational filler.
- Match each requested concept against positive structured evidence.
- Keep equivalence directional: a ceramic activity can support an art query,
  but the art category cannot support a ceramic query.
- Do not derive activities from broad category aliases (museum != ceramics,
  dessert != coffee, wine bar != beer).
- Retain literal business-name fragments and protect exact names from inferred
  date/location intent, while still enforcing explicit filters.
- Evaluate all query facts and constraints against the same branch, rather than
  assembling an imaginary offering from different branches.
- Ignore negative fact labels; explicitly asserted dietary absences such as
  sin gluten remain valid concepts. This is not unrestricted natural-language
  negation understanding.

## Controls and ordering

The existing parser handles dates, dayparts, registered locations, availability
and explicit query budgets. Content matching no longer receives its old broad
semantic hints. That older category interpretation remains presentation-only.

Exact names rank before name prefixes and structured attribute matches when the
user selects relevance. Explicit recent/price/rating order continues to win.
Manual category, location, people, budget, time, visibility and distance filters
remain mandatory. The separate feedback about unknown budgets is not fixed here.

```sh
node --test apps/mobile/scripts/test-spot-search.cjs
node --test scripts/spots-research/menupp-search-products.test.mjs
node apps/mobile/scripts/test-search-filter.cjs
node apps/mobile/scripts/test-contextual-category.cjs

```

The new suite covers new synthetic places (no named exceptions), positive and
negative matches, compound queries, same-branch facts, constraints, exact names,
ordering, immutability and real catalog regressions across several domains.

Observed in the existing local app: ceramica returns Color Me and Cafe Pintado;
pola returns seven brands; pizza Granada returns Carpaneto in Granada. Map search
for ceramica exposes Color Me and four Cafe Pintado branch markers. Browser proof
is in `output/playwright/search-global-20261101/`.

Two older checks require separate maintenance: commercial-status expects eight
Chilitaco branches but current catalog maps seven; price-sort uses a partial
module loader that cannot load registeredCommercialCenters (already an existing
dependency before this search change). No unrelated fixtures were edited.
